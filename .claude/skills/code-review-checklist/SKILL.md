# 코드 리뷰 체크리스트

코드를 **고치지 않고** 문제를 찾아 보고하는 스킬이다. 보고는 짧고 근거가 확실해야 한다.
리뷰어가 틀린 지적을 하면 사람은 그 리뷰 전체를 믿지 않게 된다. 그래서 **양보다 정확도**가 우선이다.

## 1. 리뷰 대상 정하기

1. 사용자가 파일이나 폴더를 지정했으면 그것만 본다.
2. 지정하지 않았으면 `git diff --cached`(staged)와 `git diff`(unstaged)를 본다. 둘 다 비어 있으면 무엇을 리뷰할지 물어본다.
3. 변경된 줄만 보지 말고, 그 줄이 호출하는 함수와 호출되는 곳까지 읽어서 맥락을 확인한다.
4. 테스트 파일이 있으면 함께 읽는다. 테스트가 이미 막고 있는 버그는 보고하지 않는다.

## 2. 4개 관점 체크리스트

### 정확성 (버그)
- 로직 오류, 조건 반전, off-by-one, 경계값(빈 배열, 0, 마지막 요소)
- 상태 초기화 누락: 재시작·재시도 때 이전 값이 남는지
- 같은 이벤트가 두 번 들어올 때(더블 클릭, 중복 호출)의 동작
- 타입 혼동: `===` 비교에서 문자열과 숫자, boolean이 섞이는지

### 보안
- `innerHTML`, `eval`, `new Function`, `document.write`에 외부 입력이 들어가는지
  (코드에 하드코딩된 신뢰된 데이터만 들어가면 💡 제안으로 낮춘다)
- 하드코딩된 비밀값(API 키, 토큰, 비밀번호)
- 셸 명령 조합, 경로 조작, 위험한 파일 삭제

### 가독성·유지보수
- 의도가 드러나지 않는 이름, 한 가지 이상의 일을 하는 긴 함수
- 복사·붙여넣기 중복, 죽은 코드, 주석과 코드의 불일치
- 매직 넘버, 여러 곳에서 같은 값을 따로 들고 있는 경우

### 접근성·UX
- 키보드만으로 조작할 수 있는지 (`button` 대신 `div` 클릭 등)
- 화면이 바뀔 때 포커스가 적절히 이동하는지
- 정보를 색으로만 전달하는지 (정답·오답을 색 외에 텍스트로도 알려주는지)
- 스크린리더가 변경을 알 수 있는지 (`aria-live` 등)
- 모바일 폭(360px)에서 깨지거나 가로 스크롤이 생기는지

## 3. 심각도

| 등급 | 기준 |
|------|------|
| 🔴 Critical | 데이터 손실, 보안 사고, 핵심 기능이 아예 동작하지 않음 |
| 🟠 Major | 흔한 사용 흐름에서 잘못된 결과가 나옴 |
| 🟡 Minor | 드문 경우의 오동작, 유지보수를 확실히 어렵게 만드는 문제 |
| 💡 제안 | 취향, 스타일, 있으면 좋은 개선 |

## 4. 보고 규칙

- **코드에서 직접 확인한 것만** 보고한다. "~일 수 있다"는 추측만으로는 보고하지 않는다.
- 모든 지적에 `파일:줄`을 붙인다.
- 🔴·🟠는 **재현 시나리오**(어떤 입력이나 조작 → 어떤 잘못된 결과)를 함께 적는다.
- 취향 문제는 아무리 많아도 💡로 내리고, 💡는 최대 3개까지만 적는다.
- 문제가 없으면 억지로 만들지 말고 "발견된 문제 없음"이라고 쓴다.
- 파일을 수정하거나 커밋하지 않는다. 수정은 사용자가 결정한다.

## 5. 출력 형식

```markdown
## 코드 리뷰 결과

**요약**: <한 줄. 예: 🟠 1, 🟡 2, 💡 2 — 오답 재시도 흐름에 버그 1건>
**대상**: <리뷰한 파일 또는 diff 범위>

| 심각도 | 관점 | 위치 | 문제 | 제안 |
|--------|------|------|------|------|
| 🟠 | 정확성 | `src/main.js:42` | ... (재현: ...) | ... |

### 잘된 점
- <구체적으로 1~3개>
```

표는 심각도가 높은 순서로 정렬한다.
